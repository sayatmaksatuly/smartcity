# AITU KEREK — Phase 5: итоговый отчёт

Дата: 17 октября 2026. Работа выполнена в существующем проекте на Windows, без Git push, публикации, изменения `.env`/`.env.local`, нового Supabase project или переноса POI. В рабочем каталоге нет `.git`; поэтому Git diff/commit не использовались.

## 1. Executive Summary

Реализованы лаймовый интерфейс, серверная пешеходная маршрутизация openrouteservice, подтверждённый старт и точность геолокации, Supabase Auth, профиль, постоянные настройки, избранное и сохранённые прогулки. Главная осталась простой; карта открывается только по действию. Гость может искать, общаться с помощником, смотреть карту и обращаться к routing без входа. Вход нужен для личных данных.

**Строгая Definition of Done внешних интеграций ещё не достигнута:** нет `ORS_API_KEY`; персональные таблицы Supabase возвращают HTTP 404. Код и неразрушительная миграция готовы, но живые маршруты, полный email/password flow и изоляция двух настоящих аккаунтов не подтверждены. Эти ограничения не заменены заглушками в приложении. Gemini отдельно подтверждён двумя успешными реальными генерациями. База содержит 549 настоящих POI.

## 2. Архитектура финальной платформы

React/TypeScript/Vite и Leaflet сохраняют общее состояние старта, фильтров, результата, выбранного места и чата. `useWalkingRoute` изолирует жизненный цикл маршрута и отменяет устаревшие ответы. `AccountProvider` управляет сессией и личными данными; вход не сбрасывает результаты. Сохранённые места разрешаются по актуальным SQLite ID через `/api/pois/resolve`, а не берут устаревшие факты из PostgreSQL.

FastAPI/SQLAlchemy/SQLite остаются источником городских фактов. Gemini RAG не переписан. Новый `/api/routes` получает назначения только из SQLite и обращается к фиксированному ORS HTTPS endpoint. Supabase PostgreSQL хранит исключительно персональные данные, доступ проверяет JWT/RLS. Административный импорт остался локальным CLI с прежней атомарностью; тестовые fixtures в production DB не записывались. [Подробная схема](ARCHITECTURE.md).

## 3. Новый лаймовый дизайн

Основные цвета: лайм `#B9F23D`, лесной `#193521`, текст `#18221A`, фон `#FAFCF7`, белые поверхности. Лайм выделяет CTA, активные фильтры, выбранные места и дорожную линию; большие кислотные поверхности не используются. Сохранена локальная Golos Text: хорошая кириллица и прежняя читаемость без дополнительных внешних шрифтов. Основной текст 16px, пояснения преимущественно 14px, основные действия 44–52px.

Расчёт sRGB: тёмный текст CTA на лайме **10,07:1**, вторичный текст на фоне **6,37:1**, на мягкой поверхности **5,93:1**, основной текст на белом **16,37:1**. Это проверка конкретных пар, не сертификация всего интерфейса. Главная сохраняет «Куда хотите сходить?» → запрос → результаты, без карты и обязательной регистрации.

## 4. Реализация карты

Leaflet загружается лениво. На карте: отдельный старт, нумерованные места, выбранное назначение, геометрия ORS с тёмной обводкой и лаймовой линией, fit по маршруту, возврат к результатам, изменение старта и добровольная геолокация. На мобильном доступны переключатели маршрута ко всем результатам даже при скрытом боковом списке. Пояснения пути раскрываются отдельно, дистанция и ETA видимы сразу.

Сохранена реальная стандартная OSM Carto подложка с читаемыми улицами/парками; не заявляется подключение нового коммерческого tile provider. Атрибуция OSM видна. Произвольный `VITE_TILE_URL` применяется только вместе с `VITE_TILE_ATTRIBUTION` (текст экранируется); иначе используется стандартная подложка. Автотесты не нагружают tile service: в них контролируемый tile stub. Перед production нужен provider с подходящим договором/лимитами; соблюдайте [OSM Tile Usage Policy](https://operations.osmfoundation.org/policies/tiles/).

## 5. Выбранный routing provider

Выбран **openrouteservice `foot-walking`**: официальный GeoJSON endpoint, метры/секунды, пригодный серверный REST контракт. Изучены Valhalla и GraphHopper; self-hosted Valhalla потребует отдельной инфраструктуры. Публичные demo endpoints не используются. Ключ только в backend Authorization header, endpoint фиксирован, redirects/retries отключены.

Ограничения приложения: 1–3 POI, необязательное возвращение, область Астаны, snapping до 250м, ответ до 2MB/20 000 координат, 20 запросов/минуту и два одновременных на процесс. Это собственные ограничения, не обещание тарифа ORS. Лимиты и условия аккаунта нужно сверить при выдаче ключа. [Сравнение провайдеров, источники и контракт](PHASE5_ROUTING.md).

## 6. Геолокация и маршруты

GPS запрашивается только кнопкой, с `maximumAge=0`, `enableHighAccuracy=true`, timeout10с. Обрабатываются отказ, недоступность, timeout и отсутствие secure context. Точность показывается числом и окружностью; маркер «Вы здесь» появляется только для полученного GPS. Центр Астаны остаётся явно указанной исходной точкой и перед маршрутом требует подтверждения. Есть ручные координаты, выбор названия из SQLite и отдельный режим клика карты.

Смена старта при активном маршруте пересчитывает путь и сохраняет результаты; старые карточные оценки помечаются как относящиеся к прежнему старту. Поздний GPS после закрытия окна/навигации игнорируется. GeoJSON `[lon,lat]` преобразуется в Leaflet `[lat,lon]`. При отсутствии ключа, сети или пути синтетической линии нет. Нажатие «Маршрут» передаёт подтверждённый старт и публичные POI провайдеру; приложение не сохраняет GPS.

Для нескольких мест пользователь сам выбирает порядок остановок. Дорога и возвращение считаются ORS; примерные посещения добавляются отдельно. Невыполнимая по бюджету последовательность явно обозначается, кнопка сохранения как готовой прогулки недоступна. Подборку можно сохранить отдельно до построения пути. ETA приблизительное, доступность входов и фактическое состояние дорожек не гарантируются.

## 7. Supabase Auth

Официальный `@supabase/supabase-js`: регистрация, вход, выход на текущем устройстве, подтверждение email, recovery/update password, PKCE redirects, восстановление и обновление сессии. Двойные отправки блокируются. Ошибки имеют фиксированные русские сообщения, сырые SDK exceptions не выводятся. После гостевого сохранения действие повторяется после входа в текущей вкладке. Закрытие окна отменяет это намерение.

Сессия хранится SDK в localStorage; параметры callback очищаются после обмена. Recovery остаётся доступным при закрытии/повторном открытии окна и перезагрузке этой вкладки до завершения. Письмо нужно открывать в том же браузере/host для PKCE; несохранённые результаты другой вкладки не восстанавливаются автоматически. Подтверждение email не отключалось. [Точная настройка URLs, email templates и SMTP](PHASE5_SUPABASE.md).

## 8. PostgreSQL и RLS

Миграция: [`202610170001_personal_data.sql`](../supabase/migrations/202610170001_personal_data.sql). Таблицы: `profiles` (имя и allowlist настроек), `favorites` (уникальные user_id/poi_id), `saved_walks` (название, порядок ID, предпочтения, даты). ID относятся к устойчивым OSM объектам. При замене/удалении OSM объекта ссылка может стать недоступной — UI сообщает об этом.

На всех таблицах ENABLE/FORCE RLS; owner clauses основаны на `auth.uid()`. Anonymous/public доступ отозван; для authenticated разрешены только нужные операции/колонки, владелец и timestamps не редактируются. JSON не допускает координаты/произвольные поля. Удаление личных данных — атомарный security-invoker RPC под той же RLS, без удаления Auth account. Полное удаление аккаунта требует проверенной административной процедуры.

Миграция **не применена**: административный SQL доступ недоступен. Она создаёт объекты внутри транзакции, не удаляет существующие таблицы; конфликт имён прерывает применение. Есть **32 pgTAP assertions** для локальной тестовой БД, но они **не выполнялись**: CLI/PostgreSQL/Docker в окружении не подготовлены. Статический review политик не выдаётся за проверку работающей RLS.

## 9. Избранное

Действие доступно у каждой рекомендации. Состояние обновляется без reload после успешной записи. Гость получает компактный вход, сохраняя поиск; повторное сохранение уже избранного после входа не удаляет запись. Профиль заново разрешает названия через SQLite, позволяет показать место, построить маршрут и удалить сохранение. Сбой сети показывает ошибку и сохраняет имеющиеся данные.

## 10. Сохранённые прогулки и настройки

Сохраняются название, 1–3 уникальных ID в порядке посещения, разрешённые предпочтения и даты. Доступны открытие, свежий маршрут, переименование, удаление. Если исчезла хотя бы одна остановка, прежняя последовательность не подменяется молча сокращённой прогулкой. Геометрия не сохраняется. Имя и текущие настройки сохраняются в профиле отдельно; применение сохранённых настроек — явное действие, вход не меняет текущий подбор.

## 13. Security review

Реально работали основной агент и три субагента. Routing agent независимо проверил геопространственный контракт, backend reliability и React races; Supabase agent — auth, RLS/grants и хранение; UI/QA agent — доступность, мобильный UX и автоматизацию. Основной агент проверил интеграцию, privacy, bundle и продуктовую приёмку. Десять запрошенных ролей распределены между четырьмя агентами; это не десять независимых специалистов и не реальное исследование пользователей.

Исправлены: поздний chat/search response при открытии сохранённого маршрута; поздний GPS после закрытия окна; устаревшая загрузка профиля после мутации/смены аккаунта; JSON-null обход проверки настроек; необходимость блокировать privileged frontend credentials **до** bundling. Auth токены проверяет Supabase, Python не принимает user_id как доказательство доступа. OSM строки отображаются React как текст; динамическое marker HTML содержит только числа, не OSM названия. Маршрутизация и RAG имеют квоты/параллельность на процесс; внешние ошибки безопасны. Полный penetration test не проводился.

## 14. Accessibility review

Реальный screen reader, touch-устройство, полная WCAG certification не проверялись.

## 16. Известные проблемы и ограничения

Главные блокеры — ORS ключ и применение Supabase migration/redirect configuration с последующей live проверкой собственных аккаунтов. Даже успешный ORS ответ не гарантирует вход/ремонт/безбарьерность. Городские данные остаются неполными: 416 мест без часов,56 со сложным неподдерживаемым расписанием, только1 fee=no. Сложные диалоговые намерения ограничены прежними правилами. Состояние поиска/чата живёт во вкладке; оно не переносится автоматически после reload/email перехода в другую вкладку.

Process-wide quota не заменяет распределённые ограничения и мониторинг расходов. Основной JS вырос из-за SDK; отдельный Leaflet chunk сохранён, но дальнейший performance audit полезен. Нет публичного deployment, чистой установки на другом ПК, настоящего мобильного GPS/сенсорного устройства, полного screen-reader/penetration тестирования и полевых проверок улиц.

## 17. Необходимые ручные действия пользователя

1. В существующем Supabase SQL Editor применить миграцию целиком; при конфликте существующих объектов остановиться и сравнить схемы, ничего не удалять.
2. Проверить Data API/public schema, включённый email provider, exact callback URLs и SMTP по [инструкции](PHASE5_SUPABASE.md). Подтверждение email оставить включённым.
3. Получить ключ ORS согласно условиям аккаунта, самостоятельно добавить **только** `ORS_API_KEY` в `backend/.env`, перезапустить backend. Не передавать его frontend.
4. На своих двух тестовых аккаунтах проверить email/signup/login/recovery, RLS отрицательные операции, избранное, прогулки, reload/logout. Выполнить pgTAP на отдельной локальной тестовой БД.
5. Отдельно подтвердить живой ORS путь в Астане и корректность длины/ETA. До этого не объявлять live routing рабочим.
