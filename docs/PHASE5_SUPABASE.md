# Аккаунты и персональные данные Phase 5

## Что реализовано

Официальный `@supabase/supabase-js`: email/password регистрация и вход, подтверждение email, PKCE redirect, восстановление и изменение пароля, восстановление сессии, выход на текущем устройстве. Сессия хранится SDK в localStorage браузера и обновляется автоматически. Вход открывается по действию пользователя; поиск, чат, карта и маршруты доступны гостю. Незавершённое сохранение хранится в памяти вкладки и повторяется после входа без сброса результатов. При закрытии диалога пользователь отменяет отложенное действие. При переходе по письму в другой вкладке нельзя обещать восстановление несохранённого состояния исходной вкладки; для PKCE используйте тот же браузер.

Профиль содержит email (Supabase Auth), редактируемое имя и постоянные настройки подбора (`profiles.preferences`). Кнопка «Сохранить текущие настройки» сохраняет время, категории и условия; «Применить сохранённые настройки» явно восстанавливает их. Вход не меняет активные фильтры автоматически. `favorites` хранит только стабильный OSM ID. `saved_walks` хранит название, 1–3 разных OSM ID в порядке посещения и разрешённые настройки времени/категорий/режима. Нет координат старта, текста чата или геометрии маршрутов. Имена и факты о местах заново разрешаются из SQLite через `/api/pois/resolve`; исчезнувшее место не разрушает список сохранений. Городская база не переносилась в Supabase.

Идентификаторы импорта уже имеют формат `node/123`, `way/123`, `relation/123`: `backend/app/services/importer.py` формирует ID из типа OSM и исходного числового ID, а не из номера строки SQLite. Повторный импорт того же объекта сохраняет ID. При удалении/пересоздании объекта OSM или выборе другого представителя дедупликации сохранённый ID может исчезнуть; UI сообщает об этом.

## Необходимая настройка существующего проекта

1. Не меняя действующий проект, откройте **Supabase Dashboard → SQL Editor → New query**. Выполните целиком [`202610170001_personal_data.sql`](../supabase/migrations/202610170001_personal_data.sql). Миграция в транзакции, без `DROP`, без удаления или замены существующих таблиц. Если таблицы/функции с этими именами уже есть, она прервётся и откатится: сначала сравните существующую схему, не удаляйте её. Файл рассчитан на однократное применение; внесите его в историю миграций принятого в проекте процесса.
2. **Authentication → Providers / Sign In → Email**: email/password разрешён, подтверждение email сохраняется включённым. Для писем в production настройте **Authentication → SMTP Settings**: встроенная тестовая доставка имеет ограничения адресатов и частоты.
3. **Authentication → URL Configuration**: Site URL — `http://127.0.0.1:5173`. В Redirect URLs добавьте точные URL:
   - `http://127.0.0.1:5173/?auth=confirm`
   - `http://127.0.0.1:5173/?auth=recovery`
   - `http://localhost:5173/?auth=confirm`
   - `http://localhost:5173/?auth=recovery`
   Используйте одно и то же имя хоста и браузер для запроса письма и перехода: PKCE verifier хранится в браузере. При смене порта добавьте соответствующие URL. Для production замените Site URL на HTTPS адрес и добавьте точные callback URL этого домена; не используйте широкие wildcard в production.
4. **Authentication → Email Templates**: стандартная `{{ .ConfirmationURL }}` должна сохраняться в ссылках подтверждения и восстановления. Если шаблоны ранее изменяли и они ведут только на `{{ .SiteURL }}`, восстановите стандартную confirmation URL: SDK должен получить код через Supabase verify endpoint.
5. **Project Settings → API / Data API**: Data API включён и схема `public` доступна. Миграция явно выдаёт минимальные grants даже в проектах без автоматической выдачи доступа. В frontend используются только существующие `VITE_SUPABASE_URL` и `VITE_SUPABASE_PUBLISHABLE_KEY`. Backend параметры `SUPABASE_URL`/`SUPABASE_PUBLISHABLE_KEY` проверены на наличие; аккаунтный клиент общается непосредственно с Supabase и не требует административного backend ключа.

`.env` и `.env.local` не изменялись. Пример без значений: [`frontend/.env.example`](../frontend/.env.example). Publishable/legacy anon ключ предназначен для браузера; secret/service_role запрещён. Vite останавливает dev/build при обнаружении privileged Supabase ключа или лишнего `VITE_*` параметра с именем credentials; клиент дополнительно отклоняет secret/service_role конфигурацию. `scripts/check_bundle_secrets.py` проверяет bundle без вывода значений. Никогда не помещайте приватный ключ в frontend environment.

## RLS и удаление данных

На трёх таблицах включены и принудительно применяются RLS. Все политики ограничивают строки `(select auth.uid()) = id/user_id`, доступны только `authenticated`; переданный клиентом user_id проверяется PostgreSQL. Для `anon` и `public` отозваны таблицные privileges. `authenticated` получает только SELECT/DELETE и узкие INSERT/UPDATE по колонкам. Нельзя изменять владельца, ID и созданные сервером timestamps. Избранное уникально по `(user_id, poi_id)`. JSON настроек разрешает только известные ключи и типы, исключает координаты и произвольный текст. SQL функция проверки отклоняет JSON null и дублирующиеся/невалидные POI ID.

«Удалить мои сохранённые данные» после отдельного явного подтверждения вызывает атомарную `aitu_delete_my_personal_data()`. Это **security invoker** с пустым search_path, под теми же RLS; функция очищает только имя, избранное и прогулки текущего пользователя. Его запись Auth/email остаётся. UI честно объясняет разницу. Для полного удаления аккаунта администратор должен проверить запрос пользователя и удалить запись **Authentication → Users**; FK `ON DELETE CASCADE` очистят персональные таблицы. Административный ключ в браузере и фиктивная кнопка удаления аккаунта отсутствуют.

Сырые ошибки SDK, токены, email и запросы не логируются. UI показывает фиксированные русские ошибки, пользовательский текст выводится React как текст. Операции записи защищены от двойного нажатия. При смене аккаунта данные очищаются до загрузки новых; завершившийся запрос старой сессии не меняет отображаемые данные нового пользователя.

## Проверки и честный статус

17 октября 2026 выполнен **реальный, только читающий** `scripts/check_supabase.py`:

- оба требуемых frontend и backend параметра присутствуют; значения не выводились;
- Auth settings — HTTP 200; email provider включён; signup разрешён; автоматическое подтверждение email выключено;
- `profiles`, `favorites`, `saved_walks` — HTTP 404: таблицы отсутствуют или не опубликованы через Data API;
- миграция **не применена**: доступных административных credentials/SQL соединения нет;
- настоящая регистрация, получение письма, вход, запись данных и изоляция двух реальных аккаунтов **не проверены**. Чужие email и фиктивные live-аккаунты не использовались.

Повторить безопасную проверку: `.venv/Scripts/python.exe scripts/check_supabase.py`. Она печатает только фиксированные статусы и числовые HTTP коды. Успешный Auth settings не является доказательством успешного login/email flow.

`supabase/tests/personal_data_rls.sql` содержит 32 pgTAP проверки политик, grants, отрицательных сценариев, границ данных и изоляции удаления между двумя синтетическими UUID. Он предназначен **только для локальной тестовой БД** (`supabase test db`), добавляет тестовые записи в транзакции и завершает `ROLLBACK`. Отправка писем отсутствует. Тесты PostgreSQL в этой среде не выполнялись: Supabase CLI/локальная PostgreSQL не подготовлены. Наличие SQL проверок не доказывает RLS в существующем облачном проекте.

После применения миграции проверьте на двух принадлежащих вам тестовых аккаунтах: A создаёт имя/избранное/прогулку; B не видит их и получает отказ при INSERT с user_id=A, при UPDATE ID/владельца и доступе анонимным клиентом. Проверьте регистрацию → письмо → вход, recovery → новый пароль, reload, logout, сохранение гостем → вход → повтор действия, переименование/удаление и удаление только данных A. Не используйте service_role для проверки RLS: он обходит политики.
